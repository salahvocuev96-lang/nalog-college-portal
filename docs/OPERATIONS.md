# Эксплуатация и обслуживание

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_PATH` | `data/portal.db` | файл базы SQLite |
| `BACKUP_DIR` | `data/backups` | папка резервных копий |
| `DEMO_MODE` | включён | `false` отключает быстрый демо-вход и сброс демо-данных |
| `FORCE_SECURE_COOKIES` | выкл. | всегда ставить флаг `Secure` на cookie (если HTTPS завершается до прокси без заголовка `X-Forwarded-Proto`) |
| `PORT` | 3000 | порт сервера |

## Запуск на сервере

```bash
npm ci
```

```bash
npm run build
```

```bash
DEMO_MODE=false DATABASE_PATH=/var/lib/portal/portal.db npm start
```

Перед приложением должен стоять обратный прокси с HTTPS (nginx, Caddy), передающий заголовок `X-Forwarded-Proto`. Процесс нужно запускать под отдельным пользователем через systemd или в контейнере с автоматическим перезапуском.

Проверка доступности для мониторинга: `GET /api/health` возвращает `{"status":"ok"}`, персональных данных в ответе нет.

## Резервное копирование

- Вручную: кабинет технического администратора, кнопка «Создать копию». Выполняется `VACUUM INTO`, это целостная копия работающей базы.
- Автоматически (нужно настроить): ежедневная задача cron, которая копирует базу командой `sqlite3 portal.db ".backup '/backup/portal-$(date +%F).db'"`, хранит копии 30 дней и отправляет их за пределы сервера.
- Восстановление: остановить сервер, заменить файл базы копией, удалить файлы `-wal` и `-shm`, запустить сервер. Раз в квартал проверяйте восстановление на тестовом сервере.

## Обновления

1. Обновить зависимости (`npm outdated`, затем `npm update`; мажорные версии отдельно).
2. Выполнить `npm run typecheck`, `npm test` и `npm run build`. Это же делает CI (`.github/workflows/ci.yml`) на каждый push.
3. Сделать резервную копию.
4. Развернуть. Новые миграции из `db/migrations` применяются автоматически при старте. Уже применённые миграции не редактируются: любые изменения схемы оформляются новым файлом `NNN_*.sql`.

## Что нужно для настоящей эксплуатации

Прототип показывает работающие сценарии, но перед реальной работой с данными студентов нужно:

1. **Юридическое.** Персональные данные несовершеннолетних подпадают под 152-ФЗ: нужны согласия, локализация данных в РФ, модель угроз, приказ о назначении ответственных. Это решение руководства колледжа и юристов, а не только разработчиков.
2. **Инфраструктура.** Хостинг в РФ, HTTPS, PostgreSQL с репликацией вместо SQLite (см. ARCHITECTURE.md), автоматические резервные копии вне сервера, мониторинг и оповещения.
3. **Безопасность.** Независимый аудит безопасности или пентест, ограничение частоты запросов на уровне прокси, политика паролей, по возможности вторая ступень входа для сотрудников, журнал аудита в отдельной схеме с правом только на добавление, регулярное обновление зависимостей.
4. **Данные.** Импорт реальных списков студентов, родителей и преподавателей; удаление 12 демо-групп; утверждённые правила итоговых оценок; настоящие границы семестров.
5. **Процессы.** Регламент выдачи доступа и восстановления паролей, ответственный за техническое обслуживание, обучение преподавателей, канал поддержки пользователей.
6. **Доработки.** Email-уведомления и восстановление пароля по почте, сдача заданий файлами, экспорт ведомостей, при необходимости интеграция с внешними системами.

Объём и стоимость этих работ зависят от решений колледжа. Гарантировать «работу без обслуживания» нельзя: системе нужны ответственный администратор и регулярные обновления.
