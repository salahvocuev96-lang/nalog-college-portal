# Архитектура Education Portal

## Анализ исходного состояния

До переработки было два отдельных проекта:

1. **`2p1`**: сайт расписания на GitHub Pages: один `index.html` (около 1200 строк, чистый JavaScript) и `all-groups.json` с расписанием 22 групп. Возможности: выбор группы с поиском, дни недели, живой таймер пары и перемены, тёмная тема. **Этот репозиторий не изменялся.**
2. **`nalog-college-portal` v0.1**: прототип на Next.js 15, React 19, TypeScript и Tailwind CSS 4, собранный как статический сайт для GitHub Pages. Расписание уже было импортировано из `2p1`.

Проблемы прототипа v0.1, которые потребовали переработки:

| Проблема | Почему критично | Решение в v0.2 |
|---|---|---|
| Все данные и проверки прав в браузере (LocalStorage) | Права были только видимостью: любой мог открыть консоль и поменять оценки или увидеть чужие данные | Серверная часть Next.js, база SQLite, проверка прав на сервере |
| Вход без пароля, выбор любого человека из списка | Нет учётных записей | Пароли (scrypt), сессии, временный пароль, смена при первом входе |
| Изменения видел только тот браузер, где они сделаны | Оценка преподавателя не доходила до студента | Общая база на сервере |
| Неверное время пар (08:30–10:00…) | Расходилось с реальным расписанием | Время перенесено из `2p1`: 09:00–10:30, 10:35–12:05, 12:35–14:05, 14:15–15:45, 15:55–17:25, 17:30–19:00 |
| Нет аудита, причины изменения оценки, ролей TECHNICAL_ADMIN | Требование ТЗ | Журнал аудита только для добавления, 5 ролей |

Сохранено из v0.1: стек, доменная модель, генератор демо-данных, расчёт средних, большая часть экранов и компонентов.

## Стек

- **Next.js 15 (App Router) + React 19 + TypeScript**: интерфейс и сервер в одном приложении.
- **Tailwind CSS 4**: дизайн-токены объявлены в `src/app/globals.css` (`@theme`).
- **SQLite** через встроенный модуль Node.js `node:sqlite`: без внешних сервисов и нативных зависимостей. SQL написан переносимо, чтобы позже перейти на PostgreSQL (см. ниже).
- **zod**: проверка входных данных каждого действия на сервере.
- **Vitest**: автоматические тесты бизнес-логики и прав доступа.

Supabase и Motion for React сознательно не подключались. Supabase требует внешнего сервиса и ключей, для демо достаточно встроенной базы. Анимации сделаны на CSS (keyframes в `globals.css`): они легче библиотеки и автоматически отключаются при `prefers-reduced-motion`.

    auth.ts           пароли, сессии, учётные записи, защита от подбора

    http.ts           текущий пользователь, CSRF-проверка, cookie
  lib/                общий код сервера и интерфейса
    types.ts, db-types.ts   доменная модель
    access.ts         правила доступа
    stats.ts          средний балл, итоговая оценка, посещаемость
    dates.ts          даты, учебные периоды, время пар

## Как проходит запрос

1. Браузер открывает кабинет. `AppShell` запрашивает `GET /api/session`.
2. Сервер по cookie находит сессию и строит **снимок** данных (`scope.ts`): часть базы, разрешённую роли.
3. Экраны работают со снимком: фильтруют, считают средние, строят таблицы.
4. Любое изменение отправляется как `POST /api/action { type, payload }`.
5. Диспетчер (`actions/index.ts`) проверяет сессию и запрет действий до смены временного пароля, затем выполняет обработчик **в транзакции**.
6. Обработчик проверяет данные (zod) и права (`access.ts`), пишет в базу через `repo.ts`, добавляет запись аудита и уведомления.
7. При ошибке транзакция откатывается, кэш перечитывается из базы. В ответе приходят результат и новый снимок.

Отдельного API «прочитать оценки студента X» нет, поэтому прямым запросом чужие данные не получить: сервер отдаёт только снимок текущего пользователя. Это проверяется тестами `tests/access.test.ts`.

## Роли и права

| | Студент | Родитель | Преподаватель | Учебная часть | Тех. админ |
|---|---|---|---|---|---|
| Видит оценки | свои | ребёнка | своих групп по своим предметам (куратор: все предметы группы) | только агрегаты | нет |
| Ставит и меняет оценки | нет | нет | только по назначениям, с причиной изменения | нет | нет |
| Посещаемость | смотрит свою | ребёнка | отмечает по назначениям | агрегаты | нет |
| Задания | статус своих | смотрит | создаёт по назначениям | нет | нет |
| Сообщения | преподавателям своей группы | преподавателям ребёнка | своим студентам, родителям, учебной части | преподавателям, сотрудникам | сотрудникам |
| Справочники, расписание, назначения, аккаунты | нет | нет | нет | да | нет |
| Резервные копии, состояние системы | нет | нет | нет | нет | да |
| Журнал аудита | история своих оценок | история оценок ребёнка | история оценок своих групп | полный | только факты событий без значений |

Учебная часть намеренно не может выставлять оценки: это делает только назначенный преподаватель. Технический администратор не получает учебных данных и не может изменить оценки через приложение.

## Модель данных

Основные таблицы (`db/migrations/001_init.sql`):

- `groups`, `students`, `parents`, `parent_children`, `teachers`, `staff`, `subjects`: справочники. Количество групп, курсов и специальностей не зашито в код.
- `teaching_loads`: назначения «преподаватель + предмет + группа». **Именно они дают доступ к журналу.**
- `schedule_slots`: расписание; уникальность `(группа, день, пара)`.
- `grades` (значение строго 2–5) и `attendance` (`late` / `absent` / `sick`; «присутствовал» = записи нет): **раздельные таблицы**.
- `homework`, `homework_progress` (`in_progress` / `done`; «новое» и «просрочено» вычисляются).
- `messages`, `notifications`.
- `users` (id совпадает с id человека), `sessions` (хеш токена), `password_reset_requests`.
- `settings`: границы семестров и правило итоговой оценки.
- `audit_log`: **только добавление**, триггеры запрещают `UPDATE` и `DELETE`.

## Интеграция расписания из проекта 2p1

- Источник: `2p1/all-groups.json`, копия в `src/data/groups.json`. Обновляется командой `npm run sync-schedule -- <путь к all-groups.json>`. Скрипт только читает исходный файл.
- При первом запуске генератор (`server/seed.ts`) превращает расписание в таблицы: преподаватели и предметы нормализуются («Наумова» и «Наумова Е.М.» — один человек, «(дистант)» убирается из названия), назначения получаются из расписания, «Час куратора» определяет куратора группы.
- В платформе одна база расписания: журнал, дневник и расписание используют одну таблицу `schedule_slots`. Две независимые базы не подключаются.
- Перенесённые функции: время пар, выбор группы с поиском, дни недели, живой статус пары с обратным отсчётом и полосой прогресса (`features/shared/Schedule.tsx`).
- Новое: просмотр по неделям, расписание преподавателя, переход от занятия к журналу, редактирование учебной частью с проверкой конфликтов и уведомлениями.
- 12 дополнительных демо-групп получили копию расписания группы того же курса и специальности. Они помечены `is_demo` и не участвуют в проверке конфликтов. В реальной эксплуатации их нужно удалить или заполнить настоящим расписанием.
- **Важно:** после переноса источником истины становится база платформы. Если расписание продолжат вести в `2p1`, его нужно повторно импортировать. Для рабочей версии лучше вести расписание только в платформе, а сайт `2p1` либо оставить как есть, либо перевести на чтение из API платформы (это будущая задача, требующая вашего решения).

## Переход на PostgreSQL / Supabase

1. Перенести `001_init.sql`: `INTEGER PRIMARY KEY AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`, триггеры аудита → функция plpgsql с `RAISE EXCEPTION`, `INTEGER` для флагов → `boolean`.
2. Заменить `sqlite.ts` и SQL в `repo.ts` и `auth.ts` на драйвер `pg`. Интерфейс `repo` не меняется, поэтому экраны и действия остаются прежними.
3. Убрать кэш всей базы в памяти: для сотен тысяч оценок выборки снимка нужно перенести в SQL-запросы с фильтрами по роли.
4. В Supabase дополнительно включить Row Level Security как второй рубеж защиты, даже если доступ к базе идёт только с сервера.
5. Вынести `audit_log` в отдельную схему, где у пользователя приложения есть только право `INSERT`.
